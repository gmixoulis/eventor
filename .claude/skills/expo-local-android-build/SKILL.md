# Local Android release build from a clean checkout

Build the APK from a separate detached checkout of one pinned commit, not from the working tree. Uncommitted edits and a running dev server would otherwise leak into the build and slow it.

- Checkout: `git checkout -q -f --detach <sha>` in a sibling build directory. Record the sha you install. Fetch it into that clone first (`git fetch -q <main-repo-path> main`), then confirm `git log --oneline | head -1` in the build directory shows the sha before Gradle runs.
- Order: `pnpm install --frozen-lockfile`, then `npx expo prebuild --platform android --no-install`, then `cd android && ./gradlew assembleRelease -PreactNativeArchitectures=arm64-v8a`.
- Export `ANDROID_HOME` to the command-line tools path on this Mac before Gradle runs.
- Run the build in the background with a 600 s timeout and read the logs. Confirm with `grep -E "BUILD (SUCCESSFUL|FAILED)"` and `grep -E "What went wrong" -A12`, not from the exit line alone.
- Install with `adb -s <serial> install -r app/build/outputs/apk/release/app-release.apk`, then confirm the new build is running before testing it.
- Before Gradle starts, check for another session that cleans caches on this Mac (a storage-cleanup session that deletes `~/.gradle`). If the Gradle cache disappears mid-build, the build fails the same way each time; one day of v0.4 builds lost two runs this way. Pause the cleanup session, or wait for it to stop, then build.
- Do not boot the emulator while Gradle runs on the same Mac. Under that load (load average about 140) the emulator hung and dropped off adb (`device not found`). Start it after `BUILD SUCCESSFUL`, or before Gradle on an idle machine.
- When the user says "open the app for me to review", leave the emulator on a visible window: stop any stale instance first (`adb -s <serial> emu kill`, wait about 8 s), boot the named AVD with `-no-boot-anim -no-snapshot -memory 2048` in the background, launch with `am start -W -n <package>/.MainActivity`, dismiss the keyguard, then bring the emulator's qemu process to the front with `osascript` System Events. Confirm the front window name and take a screenshot before saying it is open. Do not start a second emulator on the same AVD; it is refused.
- Before installing, wait for `sys.boot_completed=1` and for `adb shell service check package` to report the package service. Installing while it is down can leave the install undone. A cold boot (no saved snapshot) can take many minutes; check `adb devices` again before each install.
- The `arm64-v8a` flag matches the 64-bit-only native binaries some libraries ship. Name the effect on 32-bit devices in the report.
- Before starting, check host load and gradle or dev-server processes as described in `android-screen-audit`.
- Before building, check whether the requested version already has a release. Run `git tag --sort=-creatordate | head`, `gh release list --limit 6`, then `git log --oneline <tag>..HEAD`. A user's "version 3.1" can be the tag `v0.3.1-demo`, so match the naming scheme before concluding it is missing. If the release exists and the commits after its tag touch only non-app paths (for example `process/`), report the existing release and build nothing.
- Plain-http backend: an APK that calls an `http://` backend needs Android's cleartext permission, or login reaches no backend. Build with the override that grants it, for example `TENANT=tif EXPO_PUBLIC_API_OVERRIDE=http://<backend LAN address>:8012 npx expo prebuild --platform android --no-install`, then `./gradlew assembleRelease`. The LAN address only works on the network where that backend runs, so name it in the report. Confirm a real login on the installed build before saying it works.
- Festival-tenant APK build: run the Gradle step with `TENANT=tif`, `CI=1`, `SENTRY_DISABLE_AUTO_UPLOAD=true`, and `EXPO_PUBLIC_API_OVERRIDE` set from the backend's `PUBLIC_BASE_URL` line in its `.env.shared` (read it with `grep '^PUBLIC_BASE_URL='`, never print other secret lines). Tee the Gradle output to a log in the scratchpad so the BUILD line can be grepped afterwards.
- A Gradle lint failure inside a third-party library that passes on a plain rerun is transient (memory pressure during the build). Rerun the full build once before debugging the library.
- Gradle can reuse a cached JS bundle after an env change (`EXPO_PUBLIC_API_OVERRIDE`, `EXPO_PUBLIC_OFFLINE_DEMO`). A 35 s "release" build still called the old LAN host. Always run `./gradlew createBundleReleaseJsAndAssets --rerun assembleRelease`, then confirm the installed app hits the intended host: count backend log lines since launch (`awk -v n=$N 'NR>n'` on the backend log) and check the host address in them.
- To test a localhost-only build on an emulator, run `adb -s <serial> reverse tcp:<port> tcp:<port>` so the app reaches the Mac backend as `127.0.0.1`. Clear reverses with `reverse --remove-all` before a release test. When login on the emulator reports the server is unreachable, first run `adb -s <serial> reverse --list`: the list empties after the emulator restarts, so re-add the forward and retry before blaming the backend. If the APK has a host and port baked in at build time (for example `localhost:8012` from a cached config step), prefer starting the test server on that exact port over rebuilding just to change it.
- Before blaming a forward, read the host and port the built bundle actually calls: `grep -ao 'localhost:[0-9]*' app/build/generated/assets/createBundleReleaseJsAndAssets/index.android.bundle | sort | uniq -c`. A fallback port in app config may not be the one the bundle uses, so the forward must map that exact port.
- A forward that is listed but delivers nothing can mean the Mac server listens only on IPv4 while the forward reaches it over `::1`. Bind the test server to the address the forward uses, and check `adb devices` for a second adb server, which can break forwards.
- A fresh install on an emulator shows the location and notification permission prompts before any app screen. Dismiss them with `uiautomator dump` plus a tap on "Don't allow" before judging the first screen, and do not read those prompts as a sign-in bug.
- Mapbox needs a secret access token at build time (`EXPO_PUBLIC_MAPBOX_TOKEN`). A build made without it crashed the Map tab on the emulator. Before building, check whether the token is set. With no token, the Map screen should show a non-map fallback (for example a venue list with an "Open in Maps" link), and the report must say the real map is absent. Tap the tab and count `E ReactNativeJS|MapboxConfigurationException` lines in logcat to confirm.
- A second boot of an AVD that is already running is refused. For a second test device, list the installed system images (`sdkmanager --list_installed`), create a new AVD from one with `avdmanager create avd`, and boot that one. Kill it after the review.
- Check free space on the data volume (`df -h /System/Volumes/Data`) before booting. The emulator refused to boot with about 1.9 GB free. If space is short, measure the caches and the Trash by size and ask the user before deleting anything.
- If an identical rerun passes right after a cache cleanup, the first lint failure was transient. Say so in the report, and do not change code for it.
- Build the APK last. The user's order was device tests, `geovla-review`, fixes and final gates, then the APK, so the APK is built and released from the reviewed commit only after that review. Do not build or attach an APK earlier as a checkpoint unless the user asks.
- Gates before commit. Run typecheck, lint and jest and read each result before `git commit`. Never chain `npm run typecheck >/dev/null 2>&1; echo $?` after a commit: a failing typecheck was committed first and needed a second fix commit.
- Version bump: set the new `version` and `versionCode` for the tenant in `app.config.ts` in the same commit the APK is built from. In the build copy, set the matching `versionName` and `versionCode` in `android/app/build.gradle`, then grep `versionName` to confirm.
- Release: push the branch to the builder remote, then compare the local and remote hashes. Create the release with the full 40-character sha from `git rev-parse HEAD` for `--target`; a short hash is rejected. Attach the APK with `gh release create <tag> <apk>#<name> -R <owner/repo> --target <sha> --verify-tag --latest --notes-file <file>`. Demo releases on this repo were published as Latest, not prerelease. Create the tag on the built sha first, push it, then create the release with `--verify-tag`. Before reporting, compare `shasum -a 256 <apk>` with `gh release view <tag> --json assets -q '.assets[0].digest'` (strip `sha256:`); report only a match. After install, confirm `adb -s <serial> shell dumpsys package <package> | grep versionName` shows the version you built.
